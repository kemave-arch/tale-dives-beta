## 1. What Tale Dives Is
An immersive, LLM-driven fantasy novel game. The protagonist's actions and the world's responses are generated as narrative prose by Gemini, but long-term memory, game state (inventory, codex, NPCs, factions, quests), and mechanics are tracked deterministically in client-side TypeScript structures and parsed from the LLM's structured `<sync>` output each turn. It runs purely client-side (React + Vite) with no backend, storing state in `localStorage` with optional Google Drive backup.

## 3. What's Built (Current State)
- **Tale Weaving (Inspired Mode):** A phased, generative setup flow (World → Protagonist → Cast → Lore → Arc) using the LLM to draft a rich starting state. Includes safety confirmations on generation. Tale Weaving's Arc phase also captures Narrative Events and Death/End Game Rules interactively, and world seeding (Original Mode, `lib/seeding.ts`) generates starter Narrative Events too.
- **Narrative Events:** `Campaign.narrativeEvents?: Dict<NarrativeEvent>` — condition-triggered reactive story complications (distinct from the linear `Campaign.beats[]` spine), checked client-side each turn via `lib/narrativeEvents.ts` against the same trigger vocabulary Codex Discovery uses (`flag`/`location_visit`/`npc_met`/`quest_complete`/`manual`), plus a `story` trigger where the model itself emits `<event_trip id="..." />` when a freeform prose condition is met.
- **Death Rules & End Game Rules:** `Campaign.deathRule?: 'soft_fail' | 'permadeath'` (plus `deathInstructions`) branches defeat handling between the existing recovery beat and a real story-ending death; `Campaign.endGameRules?: Partial<Record<EndingOutcome, string>>` is per-outcome narration guidance surfaced to the model on the existing `!conclude`/final-beat ending triggers.
- **NPC Kinship:** `KinshipType` (`'parent'`/`'sibling'`/`'child'`/`'spouse'`/`'mentor'`/`'clan'`) on `NpcEntry.kinship`, hard-gating INTIMACY-track escalation for family relations regardless of Trust/Affection tier.
- **XML Turn Engine:** The narrator emits a `<nar>` block for prose and a `<sync>` block (parsed by `xmlTurnParser.ts`) containing exact state updates (`<loc>`, `<npc>`, `<item>`, `<enrich>`, `<project>`, `<breakthrough>`, etc.).
- **JIT Context:** Slices the massive Codex into a small ~40-80 token header (`jitContext.ts`) injected into the prompt each turn, based on who is present or relevant.
- **Codex & Discovery:** Tracks Lore, NPCs, Factions, Locations, Items, Quests, Skills, Projects, and Bestiary. Items are gated by `DiscoveryState` (Known vs. Hidden).
- **Client-Side Image Generation:** Generates UI assets (character portraits, realm art) on the fly via Gemini (`lib/imageGeneration.ts`), storing them in IndexedDB.
- **Lore Accuracy System:** Optional, Tale-Weaving-only "Novel Inspiration / Author / Canon Scope Boundary" fields (`WorldData.sourceScope` gates this — a bare `sourceTitle` stays attribution-only, unaffected). When set, injects a lore-accuracy + spoiler-boundary contract into Tale Weaving's phase calls and every turn's JIT context (`jitContext.ts`), and resolves canon-accurate physical/environmental descriptions for NPC portraits and Location images (`lib/canonDescription.ts` — NPCs via a fixed 10-slot template, Locations as one freeform paragraph). Uses **direct references**: the entity's real name and a direct citation of the source title/author/scope both reach the image model (`imageGeneration.ts`'s `canonReferenceLine`, appended to all three `buildXPrompt` functions whenever `sourceTitle`+`sourceScope` are set) — live testing against `gemini-3.1-flash-lite-image` confirmed direct references to real novels/characters aren't refused, and a name-redacted description had produced portraits far from actual canon (an earlier iteration of this system redacted names for IP-caution reasons; reversed after that test). Continuity across regenerations is preserved via `NpcEntry.canonAppearance`/`LocationEntry.canonDescription`. Region maps get the same direct-citation treatment automatically (no separate wiring needed — `buildRegionMapPrompt` reads the same `world` object). A dev-only **Image Prompt Lab** (Settings → AI Model → Open Image Prompt Lab) drives the real prompt/resolution functions directly for iterating on wording.
- **Background Music:** Context-aware soundtrack crossfading based on turn states.
- **Turn-Time Region/Location/Area Logic:** `Player.areaId?: string` tracks which of the current `LocationEntry.areas` (if any) the player is in, cleared automatically whenever `locId` itself changes. `<turn>`'s `area`/`areadisp`/`areadesc` attributes (xmlTurnContract.ts) let the model move the player between a location's own pre-authored areas, discover a genuinely new one, or step back to the location's general space (`area="none"`) — surfaced every turn via `jitContext.ts`'s "Areas within X"/"Current Area" lines, 0 tokens for the common case of a location with none. `<turn>`'s `region`/`regiondisp`/`mapx`/`mapy` let a genuinely NEW location introduced mid-play (not just at Tale creation) get a real region assignment and 0-100 map coordinates instead of always defaulting to `region: 'Unmapped'` (`lib/locations.ts`'s `ensureLocation`) — the model reasons about placement using "Known Regions"/each known location's own region+xy (also newly surfaced in `jitContext.ts`), grounded in the Tale's own real-world source geography when a Lore Accuracy Contract is active, or Earth-like region/country proportions otherwise. `App.tsx`'s turn loop self-heals a live-caught model confusion (reaching for a brand-new `loc_id` instead of `area=""` when moving into one of the current location's own areas) by redirecting through effective_* values rather than the raw turn fields, and `lib/codex.ts`'s `{{Term|loc}}` auto-registration dedup (`isKnownAreaName`) guards the same fork one level down for inline keyword tags.
- **Data Persistence:** Client-side `localStorage` with multiple campaign slots and optional Google Drive backup/restore.
- **Narrative Settings:** Per-campaign preference dials, same pattern as Prose Depth — `Campaign.pov?: 'first' | 'third'`, `Campaign.narrationMode?: 'reactive' | 'immersive'` (Reactive narrates only the world's reaction to the player's own words; Immersive polishes the player's raw input into their character's own words/thoughts/actions as one continuous scene), `Campaign.difficulty?: TaleDifficultyConfig` (`TALE_DIFFICULTIES` in `turnContract.ts` — Chill/Easy/Balanced/Hard/Extreme, each with its own outcome-leaning guidance). All three are threaded into the prompt every turn via `jitContext.ts`, editable per-campaign in Settings → Gameplay, and set once as a final step in Tale Weaving's Story Arc phase (defaults there: Third Person, Immersive, Extreme — the last two both explicitly recommended). The `*asterisks*` Player Statement Override (turnContract.ts rule 3a) is broadened accordingly to also honor narrative/world-steering claims, not just mechanical stat claims. Prose Depth's `IMMERSIVE` tier is renamed `EXPANSIVE` (same values) since "Immersive" now names the Narration Mode setting instead.
- **Tale Weaving Protagonist Class + Starting Skills:** The Protagonist phase's `<protagonist>` tag now also drafts a `class` (a free-text archetype resolved leniently via the existing `getClassById`, same lenient by-name match used everywhere else) plus 0-3 `<skill>` tags (reusing the turn-time `skill_learn` vocabulary) for starting abilities — editable in `TaleWeaver.tsx`'s protagonist card, seeded onto the real campaign in `beginInspiredTale`. Closes a real gap where a Tale Weaving-created protagonist always started on a hardcoded generic class with zero abilities regardless of what the conversation established, unlike the older node-graph creation flow (`ProtagonistNodeModal`) which already had a real Starting Skills editor.
- **Chapter Summary, incremental redesign:** Replaced the old "cold, one-shot multi-paragraph recap" mechanism (a separate LLM call reconstructing a whole chapter's pacing after the fact at the `CHAPTER_TURN_INTERVAL` boundary — the same mechanism behind an earlier "temporal hallucination" bug) with per-turn, per-event grounding at zero extra per-turn cost. `<turn>`'s new optional `chapbeat` attribute (xmlTurnContract.ts) carries one short past-tense sentence, only on a turn that genuinely advances the story; each one is paired with that turn's own real `GameTime` into a `ChapterBeat` and appended to `Campaign.currentChapterLog` (App.tsx). At the chapter boundary the accumulated list freezes onto a synthetic `LogEntry.chapterBeats` and `currentChapterLog` resets to `[]` — no LLM round trip needed for the timeline itself, so `recapChapter`/`chapterStartTime` were removed from `App.tsx`. Presented as a vertical timeline (timestamped dots down a rail): Chronicle's own chapter-milestone card renders a closed chapter's `chapterBeats` this way (falling back to the old italic `chapterSummary` quote for a save that predates this change), and Codex's Chapters category leads with a live "Current Chapter" card showing `currentChapterLog` building in real time plus a **Pending** section (the one active Story Beat, any `advanced` quests, any triggered-but-unresolved Narrative Events) before listing archived chapters the same timeline way. `jitContext.ts`'s "Story So Far" digest now joins a closed chapter's own `chapterBeats` text directly instead of re-deriving it from a stored prose summary. A single follow-up call (`App.tsx`'s `narrateChapter`, reusing the `runSummary` provider method but fed a synthetic history built from the chapter's own frozen beats rather than raw turn history) then weaves those same accurate facts into flowing multi-paragraph prose as `LogEntry.chapterNarrative` — best of both worlds: the timeline stays the accurate, zero-cost source of truth, while a chapter still closes with a literary "previously on..." passage once that one cheap call resolves (rendered under the timeline in Chronicle's milestone card). On next resuming a Tale, if a chapter has closed since `Campaign.lastAcknowledgedChapter`, Chronicle shows a one-time "Story So Far" memo popup with that chapter's narrative (falling back to its beats, then the old `chapterSummary`, whichever is available) — dismissing it persists the acknowledgment so it won't reappear until the next chapter closes.
- **Clickable Keyword Fixes:** `[[Item]]`/`[Skill]` narration markup was previously decorative only — `onTapTerm` (opening a Codex info popup) was wired solely onto `{{Term|category}}` keyword-tag spans, so tapping a highlighted item or skill name did nothing; both now carry their own tap handler (`lib/richText.tsx`). Separately, `onTapTerm`'s `'loc'` resolution checked top-level Locations and Regions but never a location's own nested named Areas — tapping an area-tagged mention (e.g. `{{The Mess Hall|loc}}`) silently did nothing; it now falls back to opening the parent location's popup (`Chronicle.tsx`).
